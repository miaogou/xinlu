一次按键的旅程：从 /dev/mykey 到 GPIO1_IO18



本文是我学习 Linux 驱动以来第一个完整的小 demo 的教学解读。它不只是“能跑的代码”——它曾经骗过我、坑过我、也救过我。文中所有案例都是我亲身踩过的坑，我希望你读完之后，不仅会写这个驱动，还会排查这个驱动。



开场：一个曾经骗过我的程序
这段代码的第一版，曾经出现过这种错误：insmod 加载成功，串口打印出 major=249 minor=0 和 mykey init ok，一切看起来都ok。结果应用层一执行 open("/dev/mykey")，迎面撞上 No such device or address (ENXIO)。
打印成功，逻辑却失败——这是我学驱动以来最深刻的一课。破案之后发现，真凶是代码里少调了一个 cdev_add：cdev_init 只是把 file_operations 绑到了本地结构体上，相当于给门卫发了工牌，但门卫根本没上岗（没挂入内核的 cdev_map），内核按设备号查人查无此处，自然报 ENXIO。这个案例我称之为“假门卫案”，它的修复就藏在下面这份代码里。带着这个教训，我们开始看这份完整的版本。



全景地图：驱动五大块
看驱动源码之前，先给一张地图。任何一个字符设备驱动——不管驱动的是按键、LED 还是 DHT11 温湿度传感器——都是这五块的变体：
① 入口/出口（module_init / module_exit，驱动的出生与死亡）；② 设备结构体（struct key_dev，全驱动唯一的“户口本”）；③ 硬件初始化（keyio_init，把一行 GPIO 描述变成内核中独占的资源）；④ 应用接口（file_operations，open/read/release 三扇门）；⑤ 清理回退（错误路径逐级回退 + exit 逆序拆除，申请了什么就退什么）。
换硬件、换 CPU，变的只是第③块和设备树的细节，这五块的骨架永远不变。记住这张地图，看任何驱动源码都不会迷路。下面我们不按代码文件的物理顺序讲，而是跟着一次真实的按键，从应用层一路走到引脚，再走回来。
第一幕：insmod——驱动的出生
执行 insmod mykey.ko 的瞬间，内核调用 mykey_init，五块中的第①块和第③块在这里登场。
第一件事是申请门牌号。Linux 世界里每个字符设备都要有门牌号：主设备号标识哪一类驱动，次设备号标识这一类里的第几个设备。dev_t 本质是一个 u32，高位装主、低位装次。代码用 alloc_chrdev_region 向内核动态申请一个空闲号段——注意这里没有“写死设备号”的分支，因为动态申请是唯一合理的路径：写死的号一旦和系统里已有的驱动撞车，加载直接失败。
第二件事是把 GPIO 变成自己的，由 keyio_init 完成，我把它叫做“半个 probe”。它干的事本质上只有一件：把"dts 里的一行文本描述”变成“内核中一个可以操作的、被本驱动独占的 GPIO"。本版还是传统写法，编号直接算出来：GPIO1_IO18 换算成全局编号就是 (1-1)*32+18 = 18——每组 32 个引脚，第 1 组第 18 号。W8 计划改成设备树版 of_find_node_by_name + of_get_named_gpio，两版对比提取到的编号是否一致，就是很好的学习素材。
拿到编号后第一件事是 gpio_request 向内核申请独占。GPIO 是独占资源：归属的是驱动本身而不是某次打开——open 可以发生多次，但 init 只会发生一次，所以申请放在 init 而不是 open 里。申请失败会返回 -EBUSY（别人已经占了），成功返回 0。紧接着 gpio_direction_input 把引脚配成输入模式——按键是外部电路向芯片送电平，当然是读方向。这里有个容易被忽略的细节：方向配置失败时必须先 gpio_free 把刚才申请的 GPIO 放掉再退出。申请了就要放，哪怕只用了半途——这条回滚纪律是所有资源管理的通则。
第三件事是注册字符设备，也就是“假门卫案”的案发地。这三行是三位一体，必须同时出现：cdev_init 把 file_operations 的地址写进 cdev 结构——相当于写好了岗位职责；owner = THIS_MODULE 是身份注册，相当于给门卫发工牌，内核从此能查到这个 cdev 属于哪个模块；cdev_add 把设备号和 cdev 挂入内核的查找表——这一步才是门卫真正上岗。少第三步，前两步做得再漂亮，open 时内核按设备号查表查无此人，照样 ENXIO。而且 cdev_add 是有返回值的，必须检查：它失败时同样要回退前面申请的 GPIO 和设备号。



第四件事是自动生成 /dev 节点。class_create 建一个设备类（同类设备归组管理），device_create 在这个类下挂载具体设备——这两步执行完，/dev/mykey 自动出现，不用再手动 mknod。老式写法要自己 cat /proc/devices 查主设备号、自己敲 mknod 命令，节点还不会随模块卸载自动消失；class/device 这对组合把这些全自动化了。最后 atomic_set 把按键值初始化为无效键 INVAKEY，打印 init ok——这一次，是逻辑真的成功了。



第二幕：open——敲开设备的门
应用层执行 open("/dev/mykey") 时，VFS 从文件名拿到 inode，从 inode 拿到设备号，去 cdev_map 里查到我们注册的 cdev，取出 file_operations，调用其中的 .open——也就是 key_open。
这个函数只有一行实质代码：filp->private_data = &keydev。要理解它，得先分清两个参数的身份：struct inode *inode 代表持久存在的设备节点——/dev/mykey 这个文件在文件系统里的身份，你开十次它也是同一个 inode；struct file *filp 代表本次会话——你每 open 一次就新建一个，关闭就销毁。把设备结构体的地址存进 private_data，是为多实例扩展预留的接口：将来驱动两个按键，open 时就能通过 minor 区分出“你打开的是哪一个”，把对应的设备指针交给这次会话。本驱动是单实例，直接放全局的 keydev 地址即可——但接口形态从第一天就按规矩写，将来扩展不用改框架。



第三幕：read——一次按键的灵魂之旅
应用层调用 read()，进入 key_read，这是整个驱动最核心的函数。
第一件事是从 private_data 取回设备指针，然后轮询引脚电平：gpio_get_value 读 GPIO 18 的当前电平。是 0 还是 1 不是协议规定的，由硬件接法决定：本板按键一端接地，按下时电路导通拉低——所以按键闭合 = 低电平 = 0，断开 = 高电平 = 1。读到 0 就把 KEY0VALUE（0xF0）写入按键值，否则写 INVAKEY（0x00）表示无键。
写入用的不是普通赋值而是 atomic_set——原子操作。这个操作要么完整发生，要么不发生，绝不会写到一半被打断。现在这个版本其实是“为了将来”的预留：下一版要加中断，而中断可能在 read 执行的任何时刻突然插进来，也去写 key_value；如果用普通赋值，两个写操作可能互相踩、写坏数据。提前用原子变量，是为 v2 铺路，也顺便养成习惯。
读到的值在内核空间，用户程序摸不到，必须用 copy_to_user 搬运过去。这个函数的返回值设计很反直觉：它返回的不是“成功/失败”，而是还有多少字节没拷完——一种“进度报告”式的返回值。返回非 0 就是没拷干净，通常意味着用户缓冲区地址非法，此时必须返回 -EFAULT 让应用层知道出了问题。这里埋着这份代码的“雷1"：早期版本既不判断 copy_to_user 的返回值，成功时还 return 0——用户拿到垃圾数据却以为读成功了，什么都查不出来。修复后的规矩是：失败返回负错误码，成功返回实际读到的字节数 sizeof(value)。返回值是内核与应用层之间唯一的沟通渠道，含糊不得。
最后是 key_release，对应应用层的 close。注意一个细节：release 是在最后一个使用者释放时才被调，而不是每 close 一次调一次——如果有多个进程打开同一设备，只有全关了才触发。本驱动单实例，函数体为空，但 open/release 成对出现这个形态必须保持（雷4 的教训）。



第四幕：回退链——错误路径里的对称之美
mykey_init 里有一条用 goto 串起来的错误路径，是这份代码最值得品味的部分。整个初始化是一条申请链：设备号 → GPIO → cdev → class → device。任何一环失败，都必须把已经申请到手的资源按申请的逆序逐一退回：device 失败就先销 class，class 失败就先删 cdev，cdev 失败就先放 GPIO，GPIO 失败最后注销设备号。一格不多，一格不少。
再看 mykey_exit——模块卸载时执行——你会发现它就是那条回退链的完整版：device_destroy → class_destroy → cdev_del → gpio_free → unregister_chrdev_region，恰好是申请顺序的完全逆序。出口是回退链走到底的样子，两相对照，“申请与释放永远成对、顺序永远相反”这条对称思想一目了然。它和 DHT11 驱动里 remove 的对称思想一脉相承，也是你在任何内核代码里都能见到的通用纪律。



收尾：这份代码教会我的事
回头看，这不到两百行的驱动里，真正值钱的不是那几个 API 调用，而是几条可以带走的经验：打印成功不等于逻辑成功——cdev_add 不调，init ok 照样打印，open 照样 ENXIO，所以验证驱动永远要用实测行为说话；申请了就要放——资源管理看的是成对与逆序，不是心情；返回值是唯一的沟通渠道——copy_to_user 不判错，用户拿到的就是垃圾；接口形态提前按规矩写——private_data 和原子变量今天用不上，明天扩展时就不用返工。
本版是传统写法：GPIO 编号写死在代码里。下一版换成设备树 OF 链取编号，硬件描述从代码中剥离——那是通向 platform 框架的第一步。轮询版之后是中断版，之后是 platform 版：每一版都在同一副五大块骨架上换一块零件。骨架不变，零件进化——这大概就是驱动学习的全部秘密。
